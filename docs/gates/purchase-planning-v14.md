# Planejamento de compras V14
- Migração aditiva: regras por tenant/filial/SKU, FK composta, OCC, histórico imutável, eventos idempotentes e auditoria. Aplicar antes do V2. V1 permanece disponível.
- API GET/POST /api/procurement/planning. Sessão/filial verificada, fonte Neon, no-store, permissões canônicas, CSRF. Configuração exige purchases.approve; snapshots financeiros exigem as três cost.view; rascunho exige também purchases.create.
- Prazo: média de recebimentos efetivamente postados desde aprovação, 365d, amostra mínima 3 para substituir regra, não prazo até recebimento total. ABC receita 90d; GMROI 90d não anualizado, valor médio ponderado por tempo condicionado a reconciliação quantidade/valor e histórico completo; sazonalidade: média de dois meses equivalentes para próximo mês, somente 24 meses completos com vendas. Não estima demanda perdida.
- Planejador usa lotes completos, custo histórico de recebimento por fornecedor, prioridade de ruptura e retorno bruto por custo. Heurística determinística, não ótimo global, não inclui despesas; cotação atual confirmada pelo operador.
- Rascunho atômico nas tabelas canônicas, não aprova nem movimenta estoque ou caixa. Exige análise servidor gravada pelo mesmo operador até 15 minutos, revalida regras, estoque, compras abertas, demanda, orçamento e referências; idempotência. Bloqueios de tabela breves para impedir corrida com caminhos legados de pedidos; revisar escalabilidade. Aprovação/recebimento continuam no fluxo oficial.
- Ainda exige homologação ponta a ponta autenticada, regressão backend e compatibilidade da API legada de listagem/aprovação. Não publicar automaticamente. Não há dados de vendas suficientes no tenant principal para validar precisão preditiva; não fabricar registros.
